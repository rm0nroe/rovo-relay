# Copilot setup prompt

This is the single setup prompt for installation or updating an existing checkout. Copy the text below into Copilot Agent mode on the target machine.

```text
Install Rovo Relay from https://github.com/rm0nroe/rovo-relay and configure it for this project.

1. Read README.md and AGENTS.md. Detect my OS and shell. For a first installation, clone into my normal development folder and create a Python virtual environment. If the checkout already exists, inspect `git status -sb` first; update a clean checkout with `git pull --ff-only` and reuse its virtual environment. Stop and report dirty or divergent work instead of resetting, stashing or overwriting it. Install the package into that environment and run `rovo-relay --json doctor` from outside the checkout. Preserve existing local work.

2. Copy the entire included `.github/skills/ask-rovo/` directory, including `SKILL.md` and `MCP_FALLBACK.md`, into my current project without overwriting local customizations. Use package version 0.1.0a3 or newer; doctor must list `session` and report `mcp_handoff: agent_tools_with_local_guard`. Record `git rev-parse HEAD` and the executable/environment used. Version alone does not identify the installed candidate; verify the installed CLI, backend, README and both skill files match the checkout, resolving installed files from outside the checkout so local source files cannot mask an old installation. Verify the skill is available as `/ask-rovo` and can invoke the installed `rovo-relay` executable.

3. Connect to my existing signed-in normal Chrome session with Jira and Rovo using the documented requirements. Preserve tabs and unsent drafts. Do not extract cookies, start an isolated browser, or bypass browser or account restrictions. Ask for my Jira URL and expected account if needed. Before attaching, check that Chrome is version 144 or newer and the CLI runs in the same OS/user environment as Chrome (not a separate WSL, container, or remote environment). Guide me to `chrome://inspect/#remote-debugging` in that Chrome to explicitly enable remote debugging if organizational policy allows it. Explain that this grants control of the Chrome session, not just Rovo. Keep Chrome open with Rovo visible in the intended site's `/jira/` or `/browse/` tab. Other tabs may remain open; select the only eligible tab with a visible Rovo panel, regardless of the foreground tab. If no panel or multiple panels are visible, stop and ask me to leave Rovo open only in the intended tab while preserving drafts. Start `rovo-relay --site SITE --session SESSION --account EMAIL session` as one retained foreground process, keep its stdin/stdout handles open and have me approve the initial connection prompt. Read its flushed startup status JSON, including `exit_code`, before sending command lines. Do not preload an ask. If the runtime cannot retain a process and its streams, report that limitation. If the setting is missing or managed, report that blocker; do not change policy, restart Chrome with debugging flags, or fabricate a DevToolsActivePort file.


If status returns `readiness: authenticated_ui_read_only`, report account-bound mini-modal inspection only, not readiness for a live question. `active_generation: null` means unknown; `retry_safe: true` does not permit sending. Ask, list and export return `error_code: rovo_layout_unverified`; do not switch transports to bypass this limit or proceed to the live test below. The completed mini-modal report established response cards and message groups, but its fixed `Message sent.` status is not response completion. An enabled composer or disabled New chat is also insufficient. For the remaining blocker report, use only read-only observation of an already-active conversation, if one is naturally available, to identify generation start, stop/busy controls and the transition to a reliable terminal state. Do not start a question to create that state. Return only test IDs, generic control names/status wording, counts, containment, visible/enabled states and observed transitions; omit conversation/account text, private identifiers and page-specific prompt/context names. Report attachment-state indicators only if already present. If generation, attachment or transition evidence is unavailable, mark it unknown. Do not mistake dictation status, absence of a known stop button or elapsed time for completion.

If direct attachment is blocked before submission, follow the installed `/ask-rovo` skill's automatic MCP fallback. Use only Copilot's already-configured, independently permitted Playwright MCP connection. Inspect its mode and list/select the existing expected Jira/Rovo tab; verify the expected account and an idle composer without sending a question. Do not install/reconfigure tools, start a separate browser, change policy or grant new access. If MCP access is verified, use the skill's `MCP_FALLBACK.md` workflow with the local `mcp begin/finish` delivery guard for the single live test below. If it is unavailable or blocked, return the blocker report. Never switch transports after a possible submission, a missing tool result, a timeout on an ask, or `retry_safe: false`.

4. Establish readiness through the retained process's account-bound startup status with `readiness: authenticated_ui`, or through the verified MCP inspection above. `authenticated_ui_read_only` is not send readiness. For direct connection acceptance, write two `["status"]` lines sequentially to that same process, read each result and keep private evidence of one attachment and no disconnect until shutdown. Do not start separate status/ask processes or claim MCP inspection proves direct CLI attachment. Report which transport is ready. Once one is verified, confirm available Rovo credits and ask me for a repository/file that Rovo already reads successfully by hand.

5. Submit ONE question through the selected transport, asking Rovo to summarize that file and provide its source link. For direct CLI send `["ask", "--prompt-file", "PATH", "--github-source", "on"]` as one JSON line to the same process and read its result; for MCP verify the GitHub chat filter and follow the skill's guarded one-click workflow. This is one live question total across both transports, not one per transport. Use a private prompt file, never stdin as the prompt. Never automatically retry an uncertain submission or erase request records to bypass a guard. When finished, close the process's stdin and wait for exit so it detaches without closing Chrome tabs. Failed attachment or lost connection ends the session without reconnecting; generic `chrome_connection_failed` does not expand the skill's automatic MCP fallback eligibility. A completed ask can continue despite `retry_safe: false`, but never resend that turn.

Composio, Atlassian MCP, and an official Rovo CLI are not dependencies. Do not install them, enable paid usage, or change connector permissions.

Complete every unblocked step. Report installation, skill setup, authenticated browser access, and actual GitHub retrieval separately. A completed response alone does not prove successful retrieval. Stop after the one live test and report any remaining blocker.

If blocked, provide a short, copyable report for the Rovo Relay developer containing:
- OS, shell, Python version, installed Rovo Relay version, and checkout commit if available; Chrome version/channel and whether the terminal runs locally, in WSL, a container, or a remote session.
- Failed step: install, /ask-rovo discovery, doctor, browser status, or live question; include MCP connection checks, selected transport and handoff request ID if attempted.
- Exact command, exit code, error/JSON output and `attachment_elapsed_ms` if present; mark unavailable details rather than guessing. Pending approval is only a possible cause unless the prompt was observed.
- Whether Chrome remote debugging is enabled, missing or managed; whether Chrome requested approval; and whether Jira/Rovo is open and signed in.
- Whether a prompt was submitted, whether Rovo answered in the browser, and any submission_state or retry_safe values. If delivery is uncertain, say so explicitly.

For a direct connection failure with `submission_state: not_attempted` and `retry_safe: true`, collect ONE diagnostic status attempt with Chrome visible: prefix the same status command with `DEBUG=pw:browser` in macOS/Linux shells, or set that environment variable for only the diagnostic process in other shells. Capture stdout, stderr, exit code and elapsed time in private files outside Git. Record whether the connection prompt appeared and whether I approved it within the 20-second connection window; never approve it for me. Do not run ask, enable protocol tracing, increase timeouts or change endpoints. The normal JSON intentionally omits Playwright call logs. Redact the diagnostic output before sharing, including personal paths, private URLs, connection identifiers and response bodies. Preserve connection phase markers and exact error codes. A localhost `/json/version` 404 alone does not diagnose the WebSocket connection used by this CLI. If status reports an unresolved request, stop without retrying or changing records.

For unavailable MCP tools, identify the actual agent runtime/harness and the configuration it loaded, including the server command, arguments and existing-browser mode, with secrets removed. Do not assume a config path is effective or invalid just because VS Code is open. Inspect existing package-fetch/process logs for the failing package, timestamp, HTTP status and redacted block message; do not repeatedly restart npx or change registries. Report any already-approved installed/internal package source, otherwise mark it unknown. Compare project and installed SKILL.md/MCP_FALLBACK.md contents and distinguish file presence from actual `/ask-rovo` discovery. Treat Agent Browser as a candidate requiring its own approved distribution and Chrome attachment proof, not an automatic replacement.

Redact account emails, private site/repo names, personal paths, tokens, and proprietary content from the report. Preserve error wording and JSON field names around redactions. Never include cookies or browser profiles. If the error is visible only in Chrome or VS Code, include a cropped, redacted screenshot if available, or describe the visible message. Do not rerun a live request just to collect diagnostics. Leave the chat and request records intact, and never retry a possibly submitted prompt automatically.
```

Other-machine browser access and code retrieval remain unverified until this test passes.
