# Copilot setup prompt

This is the canonical Copilot setup and qualification document. For browser-bridge installation or updates, use the first prompt. To update an existing installation and prove automatic continuity with a synthetic two-question test, use the update section; for the cheapest check of a later update, use the minimal update check. To assess browserless Rovo delegation before changing the bridge, use the A2A qualification section below instead. Do not run both paths as automatic fallbacks.

```text
Install Rovo Relay CLI from https://github.com/rm0nroe/rovo-relay and configure it for this project.

1. Read README.md and AGENTS.md. Detect my OS and shell. For a first installation, clone into my normal development folder and create a Python virtual environment. If the checkout already exists, inspect `git status -sb` first; update a clean checkout with `git pull --ff-only` and reuse its virtual environment. Stop and report dirty or divergent work instead of resetting, stashing or overwriting it. Install the package into that environment and run `rovo-relay-cli --json doctor` from outside the checkout. Preserve existing local work.

2. Copy the entire included `.github/skills/ask-rovo/` directory, including `SKILL.md`, `MCP_FALLBACK.md` and `TROUBLESHOOTING.md`, into my current project without overwriting local customizations. Use package version 0.1.0a6 or newer; doctor must list `session`, `automatic conversation continuity` and `agent next action` and report `mcp_handoff: agent_tools_with_local_guard`. Record `git rev-parse HEAD` and the executable/environment used. Version alone does not identify the installed candidate; verify the installed CLI, backend, README and all three skill files match the checkout, resolving installed files from outside the checkout so local source files cannot mask an old installation. Verify the skill is available as `/ask-rovo` and can invoke the installed `rovo-relay-cli` executable.

3. Connect to my existing signed-in normal Chrome session with Jira and Rovo using the documented requirements. Preserve tabs and unsent drafts. Do not extract cookies, start an isolated browser, or bypass browser or account restrictions. Ask for my Jira URL and expected account if needed. Before attaching, check that Chrome is version 144 or newer and the CLI runs in the same OS/user environment as Chrome (not a separate WSL, container, or remote environment). Guide me to `chrome://inspect/#remote-debugging` in that Chrome to explicitly enable remote debugging if organizational policy allows it. Explain that this grants control of the Chrome session, not just Rovo. Keep the approved normal Chrome open and signed in. The CLI creates its own tab at the requested site's `/jira/for-you`, checks the expected account, opens Ask Rovo once if needed and waits up to 10 seconds for the panel/composer after navigation (separately bounded to 10 seconds). You do not need to prepare Jira or close other Rovo panels. It reuses this tab for the lifetime of the connection. Existing user tabs, drafts and active replies stay untouched. A closed owned tab can be replaced only after the unresolved-delivery guard passes; a tab navigated outside Jira is rejected without refresh. It never reloads a tab or retries submission. Multiple Chrome contexts remain an ambiguity error. Start `rovo-relay-cli --site SITE --session SESSION --account EMAIL session` as one retained foreground process, keep its stdin/stdout handles open. On the owner-authorized macOS route, verify `doctor` advertises `guarded Chrome prompt approval` and add `--approve-chrome-prompt --chrome-port PORT` using the verified port. The packaged helper performs the initial approval with no manual click; follow its dependency and exclusivity requirements in `.github/skills/ask-rovo/TROUBLESHOOTING.md`. On other routes, have me approve the initial connection prompt. If remote debugging is enabled but `DevToolsActivePort` is missing, add global `--chrome-port PORT` before `session`, using only a port advertised by that Chrome debugging UI or independently verified as owned by the intended normal Chrome process. This uses the existing loopback WebSocket and still requires Chrome approval. Do not guess a port or silently switch endpoints on failure. Read its flushed startup status JSON, including `exit_code`, before sending command lines. Do not preload an ask. If the runtime cannot retain a process and its streams, report that limitation. If the setting is missing or managed, report that blocker; do not change policy, restart Chrome with debugging flags, or fabricate a DevToolsActivePort file.


If status returns `readiness: authenticated_ui_read_only`, report account-bound mini-modal inspection only, not readiness for a live question. `active_generation: null` means unknown; `retry_safe: true` does not permit sending. Ask, list and export return `error_code: rovo_layout_unverified`; do not switch transports to bypass this limit or proceed to the live test below. The completed mini-modal report established response cards and message groups, but its fixed `Message sent.` status is not response completion. An enabled composer or disabled New chat is also insufficient. For the remaining blocker report, use only read-only observation of an already-active conversation, if one is naturally available, to identify generation start, stop/busy controls and the transition to a reliable terminal state. Do not start a question to create that state. Return only test IDs, generic control names/status wording, counts, containment, visible/enabled states and observed transitions; omit conversation/account text, private identifiers and page-specific prompt/context names. Report attachment-state indicators only if already present. If generation, attachment or transition evidence is unavailable, mark it unknown. Do not mistake dictation status, absence of a known stop button or elapsed time for completion.

If direct attachment is blocked before submission, follow the installed `/ask-rovo` skill's automatic MCP fallback. Use only Copilot's already-configured, independently permitted Playwright MCP connection. Inspect its mode and list/select the existing expected Jira/Rovo tab; verify the expected account and an idle composer without sending a question. Do not install/reconfigure tools, start a separate browser, change policy or grant new access. If MCP access is verified, use the skill's `MCP_FALLBACK.md` workflow with the local `mcp begin/finish` delivery guard for the single live test below. If it is unavailable or blocked, return the blocker report. Never switch transports after a possible submission, a missing tool result, a timeout on an ask, or `retry_safe: false`.

4. Establish readiness through the retained process's account-bound startup status with `readiness: authenticated_ui`, or through the verified MCP inspection above. `authenticated_ui_read_only` is not send readiness. For direct connection acceptance, leave existing Jira/Rovo tabs as they are and count startup status as the first operation. In a separate Copilot turn, write one `["status"]` line to that same process. Require exit 0, `tab_selection: connection_owned` and `readiness_phase: ready` for both, one new CLI tab reused without manual preparation or refresh, unchanged user tabs/drafts, one attachment and no disconnect until shutdown. Record the exact installed candidate and caller deadline. This status-only test uses no Rovo question or credits; report it separately from the retrieval test below. Do not start separate status/ask processes or claim MCP inspection proves direct CLI attachment. Report which transport is ready. Once one is verified, confirm available Rovo credits and ask me for a repository/file that Rovo already reads successfully by hand.

5. Submit ONE initial question through the selected transport, asking Rovo to summarize that file and provide its source link. For direct CLI send `["ask", "--new", "--prompt-file", "PATH", "--github-source", "on"]` as one JSON line to the same process and read its result; for MCP verify the GitHub chat filter and follow the skill's guarded one-click workflow. The initial question is one total across both transports, not one per transport. Use a private prompt file, never stdin as the prompt. Never automatically retry an uncertain submission or erase request records to bypass a guard. For direct CLI continuity acceptance, require `continuity_status: verified` and a returned `chat_id`. In a separate Copilot turn, send one distinct follow-up with plain `["ask", "--prompt-file", "FOLLOWUP_PATH"]`, without `--chat` or `--new`, asking about the preceding answer. Require the same chat ID, `conversation_mode: continued`, verified continuity and one additional visible user/assistant turn. This authorizes two live questions total for direct mode (initial plus follow-up), subject to available credits; MCP remains one question and does not prove automatic continuity. Never retry an uncertain turn. If continuity capture is unavailable or history changed, retain the completed result and report the blocker without sending again or silently using `--new`. Keep the same site/session/account for subsequent follow-ups and across restarts. Use `--new` only when I request a separate conversation; explicit observed `--chat` is an inspection/recovery override, not required for ordinary follow-ups. When finished, close the process's stdin and wait for exit so it detaches. Only its own verified empty idle legacy tab is closed; tabs with conversation content, drafts, uncertain delivery, failed preparation or unverified layouts remain with a stderr notice. User tabs stay open. Failed attachment or lost connection ends the session without reconnecting; generic `chrome_connection_failed` does not expand the skill's automatic MCP fallback eligibility. A completed ask can continue despite `retry_safe: false`, but never resend that turn.

Composio, Atlassian MCP, and an official Rovo CLI are not dependencies. Do not install them, enable paid usage, or change connector permissions.

Complete every unblocked step. Report installation, skill setup, authenticated browser access, and actual GitHub retrieval separately. A completed response alone does not prove successful retrieval. Stop after the bounded test (two direct questions, or one MCP question) and report any remaining blocker.

If blocked, provide a short, copyable report for the Rovo Relay CLI developer containing:
- OS, shell, Python version, installed Rovo Relay CLI version, and checkout commit if available; Chrome version/channel and whether the terminal runs locally, in WSL, a container, or a remote session.
- Failed step: install, /ask-rovo discovery, doctor, browser status, or live question; include MCP connection checks, selected transport and handoff request ID if attempted.
- Exact command, exit code, error/JSON output and `attachment_elapsed_ms`, `attachment_phase`, `attachment_timeout_ms`, `readiness_phase` and `readiness_timeout_ms` if present; mark unavailable details rather than guessing. Pending approval is only a possible cause unless the prompt was observed.
- Whether Chrome remote debugging is enabled, missing or managed; whether Chrome requested approval; and whether Jira/Rovo is open and signed in.
- Whether a prompt was submitted, whether Rovo answered in the browser, and any submission_state or retry_safe values. If delivery is uncertain, say so explicitly.

For a direct connection failure with `submission_state: not_attempted` and `retry_safe: true`, collect ONE diagnostic status attempt with Chrome visible: prefix the same status command with `DEBUG=pw:browser` in macOS/Linux shells, or set that environment variable for only the diagnostic process in other shells. Capture stdout, stderr, exit code and elapsed time in private files outside Git. Record whether the connection prompt appeared and whether I approved it within the 20-second connection window; never approve it for me. Do not run ask, enable protocol tracing, increase timeouts or change endpoints. The CLI emits a connection notice on stderr before the CDP call. Its 20,000 ms attachment budget does not include Playwright startup and does not override an outer terminal/tool deadline. If the caller stops sooner, record its configured deadline and termination behavior rather than assuming Chrome refused approval. The normal JSON intentionally omits Playwright call logs. Redact the diagnostic output before sharing, including personal paths, private URLs, connection identifiers and response bodies. Preserve connection phase markers and exact error codes. A localhost `/json/version` 404 alone does not diagnose the WebSocket connection used by this CLI. If status reports an unresolved request, stop without retrying or changing records.

For unavailable MCP tools, identify the actual agent runtime/harness and the configuration it loaded, including the server command, arguments and existing-browser mode, with secrets removed. Do not assume a config path is effective or invalid just because VS Code is open. Inspect existing package-fetch/process logs for the failing package, timestamp, HTTP status and redacted block message; do not repeatedly restart npx or change registries. Report any already-approved installed/internal package source, otherwise mark it unknown. Compare project and installed SKILL.md/MCP_FALLBACK.md contents and distinguish file presence from actual `/ask-rovo` discovery. Treat Agent Browser as a candidate requiring its own approved distribution and Chrome attachment proof, not an automatic replacement.

Redact account emails, private site/repo names, personal paths, tokens, and proprietary content from the report. Preserve error wording and JSON field names around redactions. Never include cookies or browser profiles. If the error is visible only in Chrome or VS Code, include a cropped, redacted screenshot if available, or describe the visible message. Do not rerun a live request just to collect diagnostics. Leave the chat and request records intact, and never retry a possibly submitted prompt automatically.
```

Other-machine browser access and code retrieval remain unverified until this test passes.

## Update and synthetic continuity acceptance

Use this on a machine where the bridge was already installed, to update it and prove automatic conversation continuity without repository retrieval. It needs commit `48677cb` or a descendant (package 0.1.0a6 or newer) and uses two Rovo questions. Pasting the first turn authorizes exactly those two, so paste it only when the account's allowance covers them. Narrow Chrome windows are supported from `48677cb`: when Jira moves Ask Rovo into the header's Show more menu, the CLI opens it from there (startup and status verified; no question has been sent at that width yet).

Paste this as the first Copilot turn:

~~~text
Update Rovo Relay CLI and run the first half of a synthetic continuity acceptance test. Follow README.md, AGENTS.md and docs/COPILOT_SETUP_PROMPT.md boundaries. This replaces the GitHub retrieval question in that document; do not ask about a repository.

1. Use the existing checkout and virtual environment. Run `git status -sb`. Leave uncommitted local changes untouched: never reset, stash, clean or overwrite them. Update with `git pull --ff-only`; if git refuses or the branch has diverged, stop and report. Require HEAD to be commit 48677cb or a descendant (`git merge-base --is-ancestor 48677cb HEAD`). Install the package into the existing environment with its existing build dependencies. From outside the checkout, run `rovo-relay-cli --json doctor`: require version 0.1.0a6 or newer, `session`, `automatic conversation continuity` and `agent next action`, and `mcp_handoff: agent_tools_with_local_guard`. Record `git rev-parse HEAD` and the executable used. Verify the installed CLI, backend, README and all three skill files (`SKILL.md`, `MCP_FALLBACK.md`, `TROUBLESHOOTING.md`) match the checkout, resolving installed files from outside it. Update the project's `.github/skills/ask-rovo/` copy without overwriting local customizations; report any differences instead.

2. Use my existing signed-in normal Chrome with remote debugging already approved. Reuse the intended site and expected account; ask me if either is unknown. Use a new dedicated session name for this test. Start ONE retained foreground process: `rovo-relay-cli --site SITE --session SESSION --account EMAIL session`, adding global `--chrome-port PORT` before `session` only if `DevToolsActivePort` is missing and the port is advertised by or verified as owned by that Chrome. Keep its stdin/stdout handles open across Copilot turns; if the runtime cannot, report that limitation and stop. Read the flushed startup JSON first: require `exit_code: 0`, `readiness: authenticated_ui`, `readiness_phase: ready`, `tab_selection: connection_owned`, and `agent next action` in `implemented`. Respect any unresolved-request guard; never clear records.

3. By pasting this prompt I authorize exactly two Rovo questions for this test (this one and the follow-up in my next turn) and confirm the allowance covers them; do not stop to reconfirm credits. Write this exact text to a private UTF-8 prompt file outside Git: "Read-only synthetic continuity test. Reply with exactly ORBIT-5826. Do not search, use tools, save memories, or change any resources." Send `["ask", "--new", "--prompt-file", "FIRST_PATH"]` as one JSON line to that process, once. Act on the result's `next` field as the installed skill describes. Require `execution_status: completed`, `continuity_status: verified`, a returned `chat_id` and `next: ask`. Record `timings_ms`. Never retry an uncertain or failed send.

4. Keep the process and its handles open, then end this Copilot turn. Report the installed commit, doctor capabilities, startup JSON fields above and the first result's `execution_status`, `continuity_status`, `next`, `timings_ms` and response text. Keep the chat ID private.
~~~

After the first turn passes, paste this as a separate Copilot turn:

~~~text
Continue the synthetic continuity acceptance test in the SAME retained rovo-relay-cli process. Inspect the previous result first; if it did not complete with verified continuity, or delivery was uncertain, stop without sending. This is the second of the two questions I authorized in the first turn.

1. Write this exact text to a second private prompt file outside Git: "Using only the preceding assistant response in this conversation, return that response in lowercase. Do not search, use tools, save memories, or change any resources." Send `["ask", "--prompt-file", "FOLLOWUP_PATH"]` once, with no `--chat` and no `--new`. Require `execution_status: completed`, the same `chat_id` as the first turn, `conversation_mode: continued`, `continuity_status: verified`, exactly one added visible user/assistant turn and response `orbit-5826`. Record `timings_ms` and `next`. Never retry.

2. Close the process's stdin and wait for it to exit. Leave the test chat, request records and my tabs in place.

3. Return a short, copyable report with account emails, site names, personal paths and chat IDs redacted: OS, shell, runtime/harness and transport; installed commit and version; doctor capabilities; startup readiness fields and elapsed attach/prepare times; both results (`execution_status`, `conversation_mode`, `continuity_status`, `next`, `timings_ms`, response text); whether the two chat IDs matched (yes/no only); visible turn count before and after the follow-up; Rovo questions used (two maximum). Mark anything unobserved as unknown. Restart continuity was not tested. Do not send further live requests or change code without a new instruction from me.
~~~

## Minimal update check

The cheapest check that an existing installation runs the current code: one Copilot turn, two Rovo questions. It covers the reinstall, `broker`, a multi-line new chat, an automatic follow-up, the timeout partial answer, `reconcile`, `chat list` and `chat export`. Outputs go to private files and only named fields are printed, so Copilot reads almost nothing. Chrome remote debugging must already be enabled, and `ROVO_RELAY_SITE` and `ROVO_RELAY_ACCOUNT` set once (see the README's install section). On macOS, give VS Code Accessibility once (System Settings > Privacy & Security > Accessibility) and accept its first request to control System Events; the broker's single Chrome prompt is then pressed automatically and you click nothing. Without that permission, Copilot asks you to start the broker yourself and click Allow once. Watch for the visual checks yourself: your active tab never changes, and the CLI's window sits tiny in the bottom-right corner.

~~~text
Run the rovo-relay minimal update check. This block is self-contained: do not read other docs or explore the repo. Record each command's exit code. Never retry a Rovo send. By pasting this I authorize exactly two Rovo questions. Check that ROVO_RELAY_SITE and ROVO_RELAY_ACCOUNT are set in this terminal (do not print them); if either is missing, ask me once. Use a new SESSION name.

1. In the existing checkout: `git status -sb` (stop if it shows local changes), `git pull --ff-only`, `git merge-base --is-ancestor 907169b HEAD`. Use the checkout's existing virtual environment by absolute path (usually `.venv`; create `.venv` and run `pip install .` in it only if none exists). Call its interpreter PY and its `bin/rovo-relay-cli` CLI. Never install into or run the CLI from system `python3` or an unqualified `python`. Run `PY -m pip install -q --force-reinstall --no-deps .`. The one allowed system-Python command is `python3 -m pip uninstall -y rovo-relay`, which removes only the copy an earlier run put there (ignore "not installed"). From outside the checkout, `CLI broker --help` and `CLI reconcile --help` must both exit 0 (output not needed).
Keep output small: redirect each CLI command's stdout to a file in a private folder outside Git and print only the fields named, using
PY -c 'import json,sys;d=json.load(open(sys.argv[1]));print({k:len(d[k]) if isinstance(d.get(k),list) else d.get(k) for k in sys.argv[2:]})' FILE FIELD...
For any step that is not PASS, also print error_code message attachment_phase submission_state empty_chat_failed.
If "$HOME/.cli-anything-rovo/broker.sock" exists, a broker I started is already running: use it and do not stop it. Otherwise, on macOS, take PORT from the first line of "$HOME/Library/Application Support/Google/Chrome/DevToolsActivePort", or else from the 127.0.0.1 port of the single `/usr/sbin/lsof -nP -a -c Google -iTCP -sTCP:LISTEN` line; start `CLI --chrome-port PORT --approve-chrome-prompt broker` in a background terminal and wait for its `ready` line. If it reports chrome_approval_failed or any other error, print error_code and message, then ask me to run `CLI broker` myself and click Allow once, and stop. Every CLI command below starts with `CLI --json --session SESSION` and runs through the broker.
2. Write q1.txt with exactly these three lines: "Read-only synthetic test." / "Reply with exactly ORBIT-5826." / "Do not search, use tools, save memories, or change any resources." Run `ask --new --prompt-file q1.txt`. Fields: execution_status continuity_status answer. PASS: exit 0, completed, verified, ORBIT-5826. Keep chat_id private; read it from the file for step 5.
3. Write q2.txt: "Using only the preceding assistant response, return it in lowercase. Do not search or use tools." Run `ask --timeout 1 --prompt-file q2.txt` (no --new, no --chat). Fields: execution_status partial_answer. PASS: exit 3, timeout, partial_answer is not ORBIT-5826 (its `next: stop` is expected; step 4 is the recovery). If it exits 0 instead, record it and skip step 4.
4. Wait 30 seconds, then run `reconcile`. Fields: execution_status submission_state answer. PASS: exit 0, completed, observed_submitted, orbit-5826.
5. Run `chat list`, fields: execution_status coverage truncated chats. Then `chat export --chat CHAT_ID`, fields: execution_status coverage messages. PASS: both exit 0; export coverage complete with at least 4 messages.
6. Stop the broker only if you started it. Reply with only a five-row table (step, PASS/FAIL, exit code, one-line note) plus OS and `git rev-parse --short HEAD`. No chat IDs, emails, site names, ports or paths.
~~~

## A2A qualification before changing the transport

Documentation checked October 22, 2026. This procedure is a Copilot acceptance test, not a claim that the installed Copilot runtime supports A2A.

The Atlassian-side switch is a built-in administration feature. Enabling it does not install an app, connect a client, or establish that the intended organization permits that client. Prefer capabilities already included in the approved environment. If the Copilot side requires a new extension, Marketplace app, Copilot Studio/Foundry resource, SDK application, custom adapter, subscription or extra approval, report that requirement and stop before adding it. Do not assume built-in means unrestricted or free usage.

- [Atlassian A2A setup](https://support.atlassian.com/atlassian-ai-gateway/docs/set-up-agent2agent-connections/) requires a compatible client and user OAuth authorization. The public Agent Card is https://a2a.atlassian.com/.well-known/agent.json; it is not an MCP endpoint.
- [Atlassian administration](https://support.atlassian.com/security-and-access-policies/docs/manage-a2a-connections-in-admin-hub/) documents the separate, organization-wide **Rovo > Agent2Agent > Allow A2A** control, disabled by default. Rovo app access and user permissions also apply.
- [VS Code's Copilot integration documentation](https://code.visualstudio.com/docs/agent-customization/mcp-servers) documents MCP connections. [Foundry Toolkit's A2A integration](https://code.visualstudio.com/docs/intelligentapps/agentbuilder) and [Copilot Studio's connected agents](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/add-agent-to-agent) run in different products. Their A2A support does not prove support in the installed editor or CLI session.
- [Copilot SDK with Microsoft Agent Framework](https://docs.github.com/en/copilot/how-tos/copilot-sdk/integrations/microsoft-agent-framework) is another documented integration path, requiring an application/runtime. It is not evidence that a native editor setting can connect directly to Rovo.

Copy this prompt into the actual Copilot session:

~~~text
Qualify browserless Atlassian Rovo A2A in THIS Copilot runtime. This is a bounded read-only acceptance test, not an instruction to install a replacement stack. Use only built-in or already-approved capabilities. New add-ons, extensions, Marketplace apps, Copilot Studio/Foundry resources, SDK applications, adapters, subscriptions and policy changes are outside scope. If any are required, report EXTRA_COMPONENT_REQUIRED, name the component and its approval/licensing requirements with official documentation, and stop before installing or provisioning it. Do not infer that enabling A2A in a personal test organization enables it in the intended organization.

1. Identify the actual product, harness, version, OS, shell and execution environment (local, WSL, container or remote). Inspect only relevant loaded configuration and available tools, with secrets redacted. Distinguish GitHub Copilot in VS Code/CLI from Copilot Studio, Foundry Toolkit and an SDK application. Do not infer capability from an extension being installed or VS Code being open. Check the official documentation for this exact runtime. Identify the existing supported A2A entry point/tool and OAuth client, or report CLIENT_CAPABILITY_NOT_ESTABLISHED. An MCP entry is not an A2A client. Do not put an Agent Card URL in MCP configuration, invent configuration keys, install packages or create an adapter.

2. Establish the intended Atlassian site, organization and account from this project's existing approved setup. If ambiguous, ask me for the site and expected account. Never substitute a personal test site for the intended site. Using my existing normal Chrome, inspect Atlassian Administration > Rovo > Agent2Agent > Allow A2A and Rovo access. Preserve tabs and drafts. Record the displayed setting; missing admin access means UNKNOWN, not disabled. Leave settings unchanged. A2A off means ORG_A2A_DISABLED. Existing Jira sign-in or MCP OAuth does not establish A2A authorization.

3. Read https://a2a.atlassian.com/.well-known/agent.json from the actual Copilot execution environment using an available HTTP client, with a bounded timeout and no credentials. Record HTTP status or exact network error, elapsed time, name, endpoint, protocol, transport and required authentication from the returned JSON. Do not disable certificate verification, copy browser credentials or retry through another environment and call that Copilot proof. Public discovery alone does not prove authorization. Confirm a supported, already-authorized A2A connection for the intended account/site. If new OAuth consent or organization access changes are required, stop with the specific setup gap and requested scopes. Complete the independent read-only checks even if another gate fails.

4. Only if client support, organization access and existing OAuth authorization are verified, send exactly ONE synthetic request through the identified A2A connection: "Read-only transport test. Reply with exactly ROVO_A2A_OK. Do not access or change Jira, Confluence, repositories or other resources." Do not use Rovo's browser chat, MCP retrieval, web search or your own model's answer as a substitute. Record the actual call, provider response and completion/error state. Retain exposed context/task/message identifiers privately; do not invent them. If delivery might have occurred but no result returns, mark UNKNOWN_DELIVERY and do not resubmit or switch transports. Respect server retry instructions without repeating a possibly accepted message.

5. End this turn after that result and retain the connection configuration and any required runtime handles for a later turn. Report separately: client capability, public discovery, organization access, OAuth readiness, actual Rovo response and browser interaction. No Jira preparation or browser focus change should be needed for the synthetic request. Record exact errors, elapsed time, caller deadline and which layer failed; do not blame the browser or increase timeouts without evidence. Save sanitized evidence outside Git; never include tokens, cookies, OAuth codes, proprietary content or personal paths in the shared report. If any prerequisite failed, stop without a live request. Do not change bridge code, request records, policies, billing or installations.
~~~

After the first synthetic request passes, send this as a separate Copilot turn:

~~~text
Continue the A2A reuse test. Inspect the previous result first; if it was incomplete, failed or delivery was uncertain, stop without sending. Using the SAME approved A2A integration and credential context, send exactly one new synthetic request: "Read-only transport test. Reply with exactly ROVO_A2A_REUSE_OK. Do not access or change Jira, Confluence, repositories or other resources." Do not prepare or focus Jira, use browser automation, start a new OAuth grant or fall back to MCP. Preserve any required client process and record its identity if applicable; A2A itself does not require one persistent local PID or TCP connection. Record the actual call/result, whether approval or sign-in was requested, browser focus changes, elapsed time and exposed identifiers. A new message ID is expected. Do not claim conversation continuity from this independent request. Never retry uncertain delivery. Close only test-owned handles/tabs when finished, retaining the approved integration and evidence. Report PASS only for two provider-backed completed responses across separate Copilot turns with no manual Jira setup; report unsupported or unknown evidence explicitly.
~~~

This proves transport and routine authorization reuse only. It does not prove conversation continuity, recovery after sleep or expired authentication, exact-commit file retrieval, or token savings. Keep the established indexing gate and exact-file comparison for retrieval acceptance; A2A availability does not fix a missing GitHub tool registration or missing repository index. A broader reliability test follows only after this small acceptance test passes.
